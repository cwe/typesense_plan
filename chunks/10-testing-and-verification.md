# Chunk 10 — Testing and verification

Status: planning. Depends on: 0. Feeds: every other chunk.

## Scope

How every other chunk proves it matches core: the local A/B harness, the live API runner, the
catalogue, acceptance criteria, test data, credentials, and where the tests live.

## What we know

- **Local A/B harness** (`plugins/typesense_search/harness/ab/`, unpushed branch): SQLite stands in
  for MySQL (tables from `dbstruct/`, core's SQL translated: full text emulated, `RLIKE`,
  `UNION`, `curdate`, `IF`, collations; accents not emulated), a private local Typesense 30.2, the
  real core `*_functions.php` and the real plugin; each case runs `do_search()` with the plugin off
  then on and compares ref sets, totals and order. 30 batteries in ~12 s; `50_combinations.php`
  generates 2,481 cases from a factorial fixture (512 resources, nine two-valued attributes) and
  checks both engines against an expected set (~2.5 min). Gotchas: `RS_TEST_MODE`; a fixture word
  must exist in the keyword table or core returns before the hook; the veto reason is read from the
  debug file.
- **Live API runner** (`harness/live/`): two users in two groups (one group Typesense-only, one
  plugin-disabled), signed requests, credentials from environment variables only, a pause between
  calls, `--slow` for date-field searches. The catalogue runner covers 269 cases in ~1 hour.
- **Catalogue** (`docs/core-search-catalogue.md`): ~300 rows, every form core accepts, with YSP
  example values, measured core/plugin totals, regenerated by a script.
- The trace (stub) harness from earlier sessions; scratch harnesses outside the repo were lost to
  the OS temp cleaner.
- The YSP test database lacks category trees, HTML fields, translated values, search filters and
  custom grants in use; a seeder tool exists for building a test system with chosen data.
- The test host's thermal limit rules out heavy MySQL batteries there. The local machine has no
  MySQL, so core's real MySQL timings can only be taken on the host.
- Credentials: API keys and the DB password are pasted per session and never stored; the
  permission system blocks reading them from other sessions' files.

## Questions to answer before coding

### Q10.1 — Where the tests live
Commit `harness/` into the plugin on `typesense` (the folder name avoids core's `tests/` scanner)
and merge the two unpushed branches? Or a separate test repository? Recommendation: in the plugin,
next to the code it tests.

### Q10.2 — The verification method
Keep both: the local harness for semantics (fast, no host) and the live A/B for counts and timing on
real data. Add CI (GitHub Actions with a Typesense container and SQLite) so every push runs the
batteries? Worth it now?

### Q10.3 — Acceptance criteria
Define "pass": identical totals and ref order for every catalogue row that core answers sensibly,
with an **accepted-divergence list** (relevance order, core bugs, decided differences) that the
runners consult. Who maintains the list, and does an unlisted difference fail the run?

### Q10.4 — Test data
Which dataset is the reference: the YSP database (real, large, limited field types) or a seeded
system (chosen data: a category tree, dynamic keywords, a date-range field, numeric fields, HTML
and translated values, related keywords, search filters, custom grants, `J`/`j*` users)? Extend the
seeder for the missing kinds?

### Q10.5 — Credentials
Keep the paste-per-session rule, or an untracked local `.env` plus a permission rule (which only
Chris can add)?

### Q10.6 — Freshness, outage and rebuild tests
The harness needs to trigger hooks, stop and restart the local Typesense, and run the worker and
rebuild in-process. Confirm these belong in the local harness rather than only on the host.

### Q10.7 — Performance tests
Measure search latency core vs plugin on the host (lightly) — which cases, what thresholds matter,
how often?

### Q10.8 — The live user matrix
Extend the two users to the permission matrix (standard, `J` with `j`/`-j`, `J` with `j*`, `R`/`h`,
`e2`, `ert`, search filter, custom grant), each as a Typesense/MySQL pair. Who creates them on the
test system, and does the group config override approach stay?

### Q10.9 — Cadence
Run the local batteries on every change; the live A/B after each chunk merge; the full catalogue
before a release. Agree?

### Q10.10 — Core bug batteries
Keep the batteries that document core's own bugs (15/16) and run them against new RS versions to see
when a bug is fixed upstream?

## Done when

The harness is in the repo and documented; the accepted-divergence list exists; a full local run and
a live run are green; new cases for each later chunk have a home.
