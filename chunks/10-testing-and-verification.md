# Chunk 10 — Testing and verification

Status: planning. Depends on: 0. Feeds: every other chunk.

## Scope

How every other chunk proves it matches core: the local A/B harness, the live API runner, the
catalogue, acceptance criteria, test data, credentials, and where the tests live.

## What we know

- **Local A/B harness** (`plugins/typesense_search/harness/ab/`, unpushed branch): SQLite stands in
  for MySQL (tables from `dbstruct/`, core's SQL translated: full text emulated, `RLIKE`,
  `UNION`, `curdate`, `IF`, collations; accents not emulated), a private local Typesense 30.2, the
  real core `*_functions.php` and the real plugin; each case runs `do_search()` with the plugin off
  then on and compares ref sets, totals and order. 30 batteries in ~12 s; `50_combinations.php`
  generates 2,481 cases from a factorial fixture (512 resources, nine two-valued attributes) and
  checks both engines against an expected set (~2.5 min). Gotchas: `RS_TEST_MODE`; a fixture word
  must exist in the keyword table or core returns before the hook; the veto reason is read from the
  debug file.
- **Live API runner** (`harness/live/`): two users in two groups (one group Typesense-only, one
  plugin-disabled), signed requests, credentials from environment variables only, a pause between
  calls, `--slow` for date-field searches. The catalogue runner covers 269 cases in ~1 hour.
- **Catalogue** (`docs/core-search-catalogue.md`): ~300 rows, every form core accepts, with YSP
  example values, measured core/plugin totals, regenerated by a script.
- The trace (stub) harness from earlier sessions; scratch harnesses outside the repo were lost to
  the OS temp cleaner.
- The YSP test database lacks category trees, HTML fields, translated values, search filters and
  custom grants in use; a seeder tool exists for building a test system with chosen data.
- The test host's thermal limit rules out heavy MySQL batteries there. The local machine has no
  MySQL, so core's real MySQL timings can only be taken on the host.
- Credentials: API keys and the DB password are pasted per session and never stored; the
  permission system blocks reading them from other sessions' files.

### Q10.3 — Acceptance criteria

with an **accepted-divergence list** (relevance order, core bugs, decided differences) that the
runners consult. Who maintains the list, and does an unlisted difference fail the run?
**Decided 2026-10-16: the acceptance rule** — for a served search the set, total and order are exact,
relevance-to-text order the only listed exception; declines must match their planned reason; core
bugs per Q11.3; unlisted differences fail; the list lives in the harness, every entry cites a
decision — decisions.md.
